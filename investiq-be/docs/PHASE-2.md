# Phase 2 — identity and onboarding

## Goal and prerequisites

Provide genuine accounts, cookie authentication, recovery/verification, profile and preference persistence, and five-question learning categorization. Requires migrated PostgreSQL, Redis and a working SMTP adapter. Compose supplies a local Mailpit inbox; no external messages or production provider credentials are needed for development.

Identity is a runnable vertical slice. Financial, contest, learning-progress, community and reward activity remain explicitly labeled previews. No existing localStorage fixture is sent to the API.

## Design and file map

- `src/investiq/models/identity.py`: eight persistence models and database constraints.
- `src/investiq/schemas/identity.py`: input/output DTOs; unknown fields and explicit null patches rejected.
- `src/investiq/services/identity.py`: rules, ownership, transaction locks, session/token lifecycle, classifications and atomic Redis rate limits.
- `src/investiq/core/security.py`: Argon2id, opaque secrets, hashes, CSRF and principal values.
- `src/investiq/api/identity.py`: HTTP contracts, cookie transport, origin/CSRF dependencies and a verified-user dependency for subsequent domains.
- `src/investiq/adapters/mail.py`: SMTP delivery behind a typed adapter.
- `src/investiq/cli.py`: operator-only role assignment with session revocation.
- `migrations/versions/0002_identity_*.py`, `migrations/questions_v1.json`: schema and an immutable snapshot of the actual frontend questions, with stable question/option IDs.
- `tests/conftest.py`, `tests/test_identity.py`: disposable PostgreSQL database, mocked mail adapter, security/concurrency tests.
- `scripts/e2e_server.py`: disposable database/API for browser tests.
- Frontend `src/api/client.js`, `src/api/services.js`, `src/app.js`: CSRF bootstrap, real identity calls, loading/errors, restore/logout, settings, security controls and email-link forms.
- Frontend `.env.example`, `playwright.config.js`, `tests/browser/identity.spec.js`: development configuration and end-to-end verification.

The service layer is analogous to Spring services with explicit transactional methods. Pydantic DTOs prevent a caller from supplying a role, owner ID, verification state or learning classification. No generic repository is introduced.

## Sessions, cookies and CSRF

An anonymous session bootstraps the CSRF token before registration/login. Authentication always rotates that session. Only SHA-256 hashes of 256-bit session and email-token secrets are stored in PostgreSQL. The session ID returned by `/me/sessions` is a revocation handle, never a login credential.

Cookie policy: HttpOnly, SameSite=Lax, `/` path, no Domain. HTTP development uses `investiq_dev_session`; production uses the Secure `__Host-investiq_session` cookie. Anonymous sessions last one hour, authenticated sessions seven days by default. The service retains at most 20 active authenticated sessions per user, revoking the oldest on a new login. Logout, explicit revocation, password recovery and operator role changes take effect in the database immediately.

The CSRF value is an HMAC derived from the unpredictable HttpOnly session secret with a fixed domain-separation message. It is returned only by `/auth/csrf`, kept in frontend memory and compared with constant-time comparison. Knowing the CSRF value does not reveal the session secret. Every mutation, including pre-auth login and registration, requires both the cookie and `X-CSRF-Token`.

Browser Origin must match the explicit CORS allowlist; Referer origin is the fallback. `Sec-Fetch-Site: cross-site` is rejected. Non-browser clients may omit Origin/Referer, but still need cookie plus CSRF. GET CSRF bootstrap also rejects foreign browser origins. All identity responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

The frontend discards CSRF after session rotation, never automatically retries a mutation, and refreshes account state when a stale CSRF value indicates another tab changed sessions. An expired session returns to login. Business previews are separate from the server's authorization boundary.

Passwords use Argon2id with 64 MiB memory, three iterations and parallelism four, off the async event loop. Registration/recovery require 12–128 characters. Login accepts existing passwords up to 128 characters and rehashes when parameters change. Unknown-account and incorrect-password login paths both perform Argon2 verification and return the same error.

## Database schema

Every application primary key is UUID, except one-to-one tables keyed by the owning user UUID and the composite onboarding response key. All dates below are TIMESTAMPTZ in UTC. Required columns are non-null unless stated otherwise. UUIDs are generated by the application. `created_at` defaults to PostgreSQL `now()`.

| Entity and purpose | Columns, constraints and indexes | Ownership and deletion |
|---|---|---|
| `users`: credentials and profile | `id` PK; `email VARCHAR(320)` unique and lowercase check; `password_hash VARCHAR(256)`; `name VARCHAR(70)` with length check; `role VARCHAR(10)` checked user/admin, default user; `active BOOLEAN` default true; nullable `email_verified_at`; `weekly_goal INTEGER` checked 35/75/105/210, default 75; `created_at`, `updated_at` | User owns their profile. Email/role/verification/password hashes are excluded from profile patches. There is no public deletion or email-change endpoint in this phase. |
| `sessions`: pre-auth and authenticated sessions | `id` PK; nullable indexed `user_id` FK; `token_hash VARCHAR(64)` unique; `created_at`; indexed `expires_at` with expiry-after-creation check; nullable `revoked_at` | Anonymous sessions have no user. Authenticated sessions belong to one user. User FK cascades on physical deletion. Active → expired/revoked; revoked rows are never revived. |
| `account_tokens`: single-use email proof | `id` PK; indexed `user_id` FK; unique `token_hash VARCHAR(64)`; checked `purpose VARCHAR(20)` verification/password_reset; `created_at`; indexed `expires_at` with expiry check; nullable `used_at` | User FK cascades. Issued → used/superseded/expired. New requests invalidate previous unused tokens of the same purpose. Verification lasts 24 hours; reset lasts 30 minutes. |
| `user_preferences`: notification choices | `user_id` PK/FK; boolean `contest`, `ranks`, `ai`, `digest` default true; `replies` default false | User-owned, cascades with user. PATCH changes only supplied keys. Actual notification delivery remains a later phase. |
| `user_privacy`: sharing choices | `user_id` PK/FK; boolean `public`, `holdings` default false | User-owned, cascades with user. Sharing itself is unavailable until the relevant domain exists. |
| `onboarding_question_sets`: approved question versions | `id` PK; unique `version INTEGER`; `questions JSONB` with stable question/option IDs; `active BOOLEAN`; `created_at` | Application-owned. No public edits. Referenced versions cannot be deleted (`RESTRICT`). Deploy a new version rather than editing the old question snapshot. |
| `onboarding_responses`: responses and derived learning profile | composite PK `(user_id, question_set_id)` FKs; `answers JSONB`; checked `experience VARCHAR(20)` beginner/intermediate/advanced; `learning_profile VARCHAR(40)`; `classification_version INTEGER`; `completed_at` | User-owned; user FK cascades, question-set FK restricts. Retaking updates the current response for that question version and records another audit event. Older question-version responses remain available. |
| `audit_events`: sensitive actions | `id` PK; nullable indexed `actor_id` FK; `action VARCHAR(64)`; nullable `resource_id UUID`; `created_at` | Application-owned. Actor FK uses SET NULL so account removal does not erase audit history. API does not expose update/delete. No secrets, raw requests, email text or tokens are stored here. |

The migration seeds one question set only: no users, administrator passwords, activity, balances, coins, achievements or classifications. JSON content is a frozen migration asset rather than an import of mutable application code.

## Transactions and concurrency

Services open a fresh AsyncSession and explicit transaction. Authenticated operations lock user first, then session, then owned resources, and recheck expiry/revocation. Recovery follows user → token → sessions, preventing two requests from consuming the same token or racing a password change against a login. Registration locks its anonymous session and relies on the unique email constraint to arbitrate duplicate registrations; the loser receives 409. Preferences/privacy are created atomically with the user.

Onboarding locks the user, checks the active question-set version, requires exactly one approved option for each of the five questions, and upserts the response in the same transaction. No XP, coins or learning score is awarded. Classification version 1 maps the experience question's first two choices to beginner, third to intermediate and fourth to advanced. Pace maps to 35/105/210/75 minutes per week. Labels are Foundation Explorer, Confident Builder and Strategy Explorer. These are educational starting categories, never financial suitability assessments.

Revoking another user's session returns 404. Non-admin access to `/admin/users/{id}` returns 403 before reading the target. The administrator profile read is audited. Future verified-only domains can use `require_verified`; Phase 2 allows an unverified owner to set up their profile and onboarding.

Redis rate limits use one atomic Lua increment/expiry operation. Defaults: 10 sensitive attempts per IP and normalized email per 15 minutes; CSRF bootstrap 60 per IP per minute. Counters contain hashed identifiers, have TTLs, and fail closed with 503 if Redis is unavailable. 429 includes Retry-After. Do not trust arbitrary forwarded IP headers; configure trusted reverse proxies explicitly when deploying. Local Vite users share the proxy's IP budget.

## API contracts

Every path is prefixed `/api/v1`. Authenticated ownership always derives from the session.

| Method / endpoint | Input / behavior |
|---|---|
| GET `/auth/csrf` | Sets anonymous cookie if needed; returns `{csrf_token: string}`. |
| POST `/auth/register` | `{email, name, password}` → 201 private profile, rotates cookie and requests verification. |
| POST `/auth/login` | `{email, password}` → 200 private profile and new cookie. Sign out first to switch accounts. |
| POST `/auth/logout` | 204; revokes session and deletes cookie. |
| POST `/auth/verification/request` | `{email}` → generic 202 message. |
| POST `/auth/verification/complete` | `{token}` → 200 message, marks email verified once. |
| POST `/auth/password-reset/request` | `{email}` → the same generic 202 message for eligible/missing accounts. |
| POST `/auth/password-reset/complete` | `{token, password}` → 200 message; consumes token, changes password, revokes every user session, deletes current cookie. |
| GET/PATCH `/me` | Read profile; patch only `{name?, weekly_goal?}`. |
| GET/PATCH `/me/preferences` | Read or patch the five notification booleans. |
| GET/PATCH `/me/privacy` | Read or patch `{public?, holdings?}` booleans. |
| GET `/onboarding/questions` | Returns version plus approved question and option IDs/text. |
| PUT `/me/onboarding` | `{version, answers: {question_id: option_id}}` → updated private profile. |
| GET `/me/sessions` | Array of at most 20 active owned session handles, current flag, creation/expiry timestamps. |
| DELETE `/me/sessions/{id}` | Idempotent 204 for an owned handle; deletes cookie if revoking current session. |
| GET `/admin/users/{id}` | Administrator-only private profile inspection, with audit event. |

Example registration input (use your own password; no example credentials are seeded):

```json
{"email":"learner@example.com","name":"Learner","password":"<12-to-128-character password>"}
```

A private profile response has this shape (IDs/times are illustrative):

```json
{
  "id":"11111111-1111-4111-8111-111111111111",
  "email":"learner@example.com", "name":"Learner", "role":"user",
  "email_verified":false, "weekly_goal":75,
  "preferences":{"contest":true,"ranks":true,"ai":true,"replies":false,"digest":true},
  "privacy":{"public":false,"holdings":false}, "onboarding":null
}
```

Example onboarding input:

```json
{"version":1,"answers":{"experience":"experience:0","learning_goal":"learning_goal:1","approach":"approach:1","interest":"interest:3","pace":"pace:1"}}
```

The resulting profile has `weekly_goal: 105` and onboarding `{version: 1, answers: {...}, experience: "beginner", learning_profile: "Foundation Explorer", classification_version: 1, completed_at: "...UTC..."}`. The server never accepts that classification from the client.

Common errors retain the Phase 1 envelope: `csrf_failed`/`origin_denied` (403), `invalid_credentials`/`session_expired` (401), `registration_conflict`/`question_version_changed` (409), `invalid_answers` (422), `invalid_token` (400), `rate_limited` (429). No response includes credential/session/email-token hashes or secrets. CSRF is intentionally the only public anti-forgery value.

## Run and verify

From `investiq-be`:

```bash
uv sync --locked
docker compose up -d --wait postgres redis mailpit
uv run --locked alembic upgrade head
uv run --locked uvicorn investiq.main:create_app --factory --reload --host 127.0.0.1 --port 8080 --no-access-log
```

Or run the API, migrations and infrastructure together:

```bash
docker compose --profile app up -d --build --wait
```

Run one API process on port 8080 at a time. In another terminal:

```bash
cd investiq-fe
npm ci
npm run dev
```

Open **http://localhost:5173** consistently, create an account, complete onboarding, then edit Settings. Open **http://localhost:8025** for local verification/reset emails and follow their links. These messages stay in the local Mailpit inbox; no external provider receives them. Use the same hostname for the UI across sign-in and email links, since cookies belong to a hostname. To use 127.0.0.1 throughout, set `INVESTIQ_FRONTEND_URL=http://127.0.0.1:5173` for a host API, or update that API environment value in Compose and recreate the service.

Mailpit is not a production mail provider. For production, configure an approved SMTP relay, verified sender, STARTTLS, credentials, HTTPS frontend URL, explicit HTTPS CORS origins and trusted proxy handling. SMTP certificate verification uses the platform trust store. Delivery happens after account/token commit; failures are audited and requests remain generic, so users can request a new link after the adapter recovers. There is no automatic retry or durable email outbox in this phase. Generic response bodies do not claim timing-based account enumeration protection; durable asynchronous delivery and production operational hardening remain Phase 12 work.

Backend checks:

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
uv run --locked alembic check
uv run --locked pytest
```

Identity tests create and drop a uniquely named database using real migrations. The configured PostgreSQL test role needs CREATEDB privileges (the local Compose role has them). They never create test accounts in your normal application database. Redis test keys have isolated namespaces and TTLs. Mail is mocked for backend tests.

Browser checks, from `investiq-fe` with local PostgreSQL/Redis/Mailpit running:

```bash
npm ci
npx playwright install chromium
npm run check
npm run build
npm run test:e2e
```

The browser suite starts a disposable API/database on 8081 and Vite on 5174, uses real local SMTP delivery, checks persistence after reload, verification, recovery, revocation, visible login errors and isolation from demo localStorage. It removes the test database on shutdown and leaves captured test emails in Mailpit. It does not reuse the developer's browser or alter real accounts. Browser traces are disabled to avoid storing credential/link data in trace artifacts.

## Operator roles

Register and verify the account first, then run from a trusted backend operator shell:

```bash
uv run --locked python -m investiq.cli set-role learner@example.com admin
# To remove administrator access:
uv run --locked python -m investiq.cli set-role learner@example.com user
```

Both actions audit the role change and revoke existing sessions. There is no public role assignment endpoint and no seeded admin password.

## Completed behavior and boundaries

Account identity, profile, onboarding answers, preferences and privacy survive reloads and new sessions. Passwords and tokens stay out of browser storage and application logs. Browser-owned demo state is preserved separately; account identity is loaded afresh from cookies and never saved into that demo record. Logout restores the separate demo experience.

Accounts can use profile/onboarding before verifying email; verified-only authorization is ready for future contest participation. Notification sending, profile/portfolio sharing, account deletion, financial activity and provider integration remain unavailable. Existing billing, contest, learning, community, reward and AI pages stay marked as previews. Phase 3 introduces stable instruments, sectors, deterministic fixture prices and explicit provenance/freshness policies.
